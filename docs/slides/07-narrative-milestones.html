Milestones vs. Commits

In Git, a commit is a snapshot of the entire repo. In Trellis, a milestone is a narrative span over a range of ops — it references, it doesn't duplicate.

Git commits

[snap1] ← [snap2] ← [snap3] ← HEAD
  │         │         │
  │         │         └── commit "fix: null auth"
  │         └──────────── commit "feat: add OAuth"
  └────────────────────── commit "init"

Each snapshot stores a full copy of the tree.

Trellis milestones

        Milestones (narrative)
        ┌────────┐   ┌────────┐   ┌────────┐
        │ "init" │───│"feature"│───│ "bugfix" │
        └────────┘   └────────┘   └────────┘
             │            │            │
  Ops:  [op1][op2][op3][op4][op5][op6][op7]
         │         │         │         │
         1-3       4         5         6-7

Ops are immutable facts; milestones are ranges over them.

Milestone Entity Structure

A milestone is stored as an entity in the EAV store — queryable via EQL-S:

Entity: milestone:def456
  ├─ type:        "Milestone"
  ├─ message:     "fix: handle null auth tokens"
  ├─ fromOpHash:  "trellis:op:abc…"   ← start of op range
  ├─ toOpHash:    "trellis:op:xyz…"  ← end of op range
  ├─ createdAt:   "2026-06-15T12:00:00Z"
  ├─ createdBy:   "identity:alice"
  ├─ affectedFile: "src/auth.ts"     (multi-valued)
  ├─ affectedFile: "src/types.ts"
  └─ parent:       "milestone:prev…"  (optional, forms DAG)

The fromOpHash / toOpHash range lets you replay exactly the ops covered by this milestone. affectedFiles is computed by scanning the ops in the range.

Auto-Proposed Milestones

The system can propose milestones by detecting logical boundaries in the causal stream:

interface MilestoneProposal {
  fromOpHash: string;
  toOpHash: string;
  suggestedMessage: string;  // AI-drafted from semantic patches
  confidence: number;        // 0-1
  reason: string;            // e.g. "Tests passed after 12 patches"
  affectedFiles: string[];
}

Built-in detection strategies:

  • Green-build boundary — propose after tests pass following changes
  • Context-switch detector — user starts editing a different module
  • Time-based — after N minutes of continuous work
  • Size-based — after N ops accumulate without a milestone

Milestone Queries

Because milestones are graph entities, they're fully queryable via EQL-S:

-- "Find all milestones by Alice"
SELECT ?m ?msg ?created
WHERE {
  [?m "type"       "Milestone"]
  [?m "createdBy"  "identity:alice"]
  [?m "message"    ?msg]
  [?m "createdAt"  ?created]
}
ORDER BY ?created DESC

-- "Find milestones touching a specific file"
SELECT ?m ?msg ?author
WHERE {
  [?m "type"       "Milestone"]
  [?m "message"    ?msg]
  [?m "createdBy"  ?author]
  [?m "affectsFile" "src/auth/provider.ts"]
}

-- "What ops are between two milestones?"
SELECT ?op ?kind ?timestamp
WHERE {
  [?m1 "toOpHash"   ?from]
  [?m2 "fromOpHash" ?to]
  (?m1 "parent" ?m2)
  [?op "hash" ?h]
  FILTER ?h >= ?from AND ?h <= ?to
}
ORDER BY ?timestamp

CLI Workflow

# Work, work, work... (causal stream records everything)

# See what's happened since last milestone
$ trellis status
  12 ops since last milestone (feature/auth-refactor)
  • src/auth.ts: symbolRename(encrypt → generateHash)
  • src/types.ts: signatureChange(AuthConfig)

# See un-milestoned ops
$ trellis log --since-last-milestone
  op5  vcs:symbolRename   encrypt → generateHash
  op6  vcs:fileModify     src/types.ts
  op7  vcs:symbolModify   AuthConfig interface

# Create a milestone from recent work
$ trellis milestone create -m "refactor: rename encrypt to generateHash"

# Milestone spans ops 5–7, covers 2 files
# A new branch pointer (or agent lane) advances too

ConceptGitTrellis
