The EAV Kernel

Entity-Attribute-Value graph store — the foundation of everything in Trellis

Source: src/core/store/eav-store.ts · src/core/query/engine.ts

Why Not Relational Tables?

The fragmentation of personal and collaborative computing is a data model problem. Tasks, notes, files, people, projects, decisions, and agent actions should not live in disconnected apps.

Relational limitations

  • Fixed schema — adding an attribute requires a migration
  • Joins are expensive and require predetermined relationships
  • No natural representation of links with semantics
  • Hard to model heterogeneous entities (files, tasks, decisions)

EAV advantages

  • Schema-agnostic — any entity can have any attributes
  • Bidirectional link traversal is native
  • Entities are identified by stable IDs, not table positions
  • Perfect for graphs, not tabular records

The EAV Triad

All data in Trellis is represented as two kinds of triples:

Fact {e, a, v}

Entity e has attribute a with value v. Values are atoms: strings, numbers, booleans, dates, or entity references.

// Entity: alice
{ e: 'identity:alice',
  a: 'displayName',
  v: 'Alice Chen' }
{ e: 'identity:alice',
  a: 'did',
  v: 'did:key:z6Mk…' }

Link {e1, a, e2}

Entity e1 is related to entity e2 via relationship a. Links create the graph structure.

// Alice authored a milestone
{ e1: 'identity:alice',
  a: 'authored',
  e2: 'milestone:def456' }

EAVStore — In-Memory Triple Store

The EAVStore maintains six indexes for fast lookups in any direction:

A catalog auto-infers attribute types, cardinality, distinct counts, and numeric ranges from observed data.

Entity Types — Thing Hierarchy

The core ontology defines a base hierarchy. Apps extend these types; they do not replace them.

Thing (core:Thing)
  ↳ Record (core:Record) — { title, description, status }
        ↳ Document (core:Document) — { content, mimeType, fileUrl }
        ↳ Event (core:Event) — { startDate, endDate }
  ↳ Collection (core:Collection) — container metadata
  ↳ Tag (core:Tag) — classification

VCS Entity Types

Beyond the core ontology, the VCS layer defines repository-specific entity types:

Repository → Branch → Milestone → Checkpoint
      ↳ FileNode → DirectoryNode
      ↳ Identity
      ↳ [AST entities: ModuleDef, FunctionDef, ClassDef, …]

Facts with Value-Level Provenance

Every Fact can carry FactMeta — provenance that rides inside the hash preimage (tamper-evident for free):

export interface Fact {
  e: string;              // entity
  a: string;              // attribute (JSONPath-style)
  v: Atom;                // value
  meta?: FactMeta;        // optional provenance
}

export interface FactMeta {
  confidence?: number;    // [0, 1] — SemType-aligned
  dataTypeId?: string;    // SemType value-node
  sources?: Source[];     // where it came from
}

export interface Source {
  authors?: string[];
  location?: { uri: string };
  loadedAt?: string;
  firstPublished?: string;
  lastUpdated?: string;
}

Actor provenance (actorType, createdById) is NOT in the fact — it belongs to the op that asserted it.

Path-Aware Ingestion

jsonEntityFacts() converts nested JSON objects into flat EAV facts using dot-notation attributes. Arrays become multiple values for the same (entity, attribute) pair.

Input:
{
  name: "Project X",
  config: {
    timeout: 30,
    retries: 3
  }
}

Output:
Fact { e, a: "name",          v: "Project X" }
Fact { e, a: "config.timeout", v: 30 }
Fact { e, a: "config.retries", v: 3 }

This is what lets the EAV store ingest file metadata, AST node properties, schema definitions — anything representable as JSON.

Time-Travel Queries

timeTravel(opHash) reconstructs the store state at any point in history by replaying ops up to (and including) a specific hash. This enables "what did the graph look like at commit X?" questions without a separate checkout.

class TrellisKernel {
  // Read all persisted ops
  readAllOps(): KernelOp[]

  // Time-travel: reconstruct EAVStore at a specific op
  timeTravel(opHash: string): EAVStore
}

This is the read-side of the causal stream — ops are the write-side (see SQLite Op-Log deck).
