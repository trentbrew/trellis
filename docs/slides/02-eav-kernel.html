Why Not Relational Tables?

The fragmentation of personal and collaborative computing is a data model problem. Tasks, notes, files, people, projects, decisions, and agent actions should not live in disconnected apps.

Limitations of tables

  • Fixed schema — migrations needed for every new attribute
  • Joins are expensive, require predetermined relationships
  • No natural graph traversal
  • Heterogeneous entities (files, tasks, decisions) need separate tables

EAV advantages

  • Schema-agnostic — any entity can have any attributes
  • Bidirectional link traversal is native (indexes on both ends)
  • Stable entity IDs — identity survives schema changes
  • One uniform model for everything: facts, files, decisions

The EAV Triad

All data is one of two kinds of triples:

Fact { e, a, v }

Entity e has attribute a with value v.

// Entity: alice
{ e: 'identity:alice',
  a: 'displayName',
  v: 'Alice Chen' }

{ e: 'identity:alice',
  a: 'did',
  v: 'did:key:z6Mk…' }

Link { e1, a, e2 }

Entity e1 is related to e2 via relationship a.

// Alice authored a milestone
{ e1: 'identity:alice',
  a:  'authored',
  e2: 'milestone:def456' }

Values are Atoms: string, number, boolean, Date, or EntityRef (string).

EAVStore — Six Indexes

The in-memory EAVStore maintains six indexes for O(1) lookups in any direction:

IndexKeyLookupMethod
EAVentity → attr → factsall facts for an entitygetFactsByEntity()
AEVattr → entity → factsall facts for an attributegetFactsByAttribute()
AVEattr → value → factsentities by valuegetFactsByValue()
link fwde1 → a → e2outgoing linksgetLinksByEntity()
link reve2 → a → e1incoming linksgetLinksByEntity()
link attra → (e1, e2)links by relationship namegetLinksByAttribute()

A catalog auto-infers attribute types, cardinality, distinct counts, and numeric ranges from observed data.

Core Ontology — Entity Types

The immutable core ontology defines a base hierarchy. Apps extend these; they do not replace them.

Thing (core:Thing)
  id, timestamps, optional tags
  │
  └── Record (core:Record)
        title, description, status
        │
        ├── Document (core:Document)
        │     content, mimeType, fileUrl
        │
        ├── Event (core:Event)
        │     startDate, endDate, …
        │
        └── Collection (core:Collection)
              title, icon, recordType
        └── Tag (core:Tag)
              classification entity

VCS extends this with Repository, Branch, Milestone, FileNode, DirectoryNode, Identity — all stored as facts in the same EAV store.

Facts with Value-Level Provenance

Every Fact can carry FactMeta — provenance stored inside the hash preimage (tamper-evident for free):

export interface Fact {
  e: string;          // entity
  a: string;          // attribute
  v: Atom;            // value
  meta?: FactMeta;    // optional provenance
}

export interface FactMeta {
  confidence?: number;  // [0, 1]
  dataTypeId?: string;  // SemType value-node
  sources?: Source[];   // where it came from
}

export interface Source {
  authors?: string[];
  location?: { uri: string };
  loadedAt?: string;
  firstPublished?: string;
  lastUpdated?: string;
}

Actor provenance (who asserted the op) lives on the op, not the fact — a fact belongs to exactly one op.

Path-Aware Ingestion

jsonEntityFacts() converts nested JSON into flat EAV facts using dot-notation attributes. Arrays become multiple values for the same (entity, attribute) pair.

Input JSON:
{
  name: "Project X",
  config: {
    timeout: 30,
    retries: 3
  }
}

Output Facts:
Fact { e, a: "name",          v: "Project X" }
Fact { e, a: "config.timeout", v: 30 }
Fact { e, a: "config.retries", v: 3 }

This is what lets the EAV store ingest file metadata, AST nodes, schema definitions — anything representable as JSON.

Time-Travel Queries

timeTravel(opHash) reconstructs the store state at any historical point by replaying ops up to that hash.

class TrellisKernel {
  // Read all persisted ops
  readAllOps(): KernelOp[]

  // Reconstruct EAVStore at a specific op
  timeTravel(opHash: string): EAVStore

  // Boot: load snapshot, then replay ops after it
  boot(): { opsReplayed, fromSnapshot }
}

The read-side of the causal stream. Write-side is the op-log (see SQLite Op-Log deck). Snapshots make boot fast — only ops after the snapshot need replaying.

High-Level Entity CRUD

The kernel exposes entity-level operations built on the raw EAV primitives:

await kernel.createEntity(
  'identity:alice',    // entity ID
  'Identity',          // type
  { displayName: 'Alice', did: 'did:key:z6Mk…' },
  [{ attribute: 'memberOf', target: 'org:acme' }]
)

const alice = kernel.getEntity('identity:alice')
// → { id, type, facts: [...], links: [...] }

await kernel.updateEntity('identity:alice', { displayName: 'Alice C.' })
await kernel.deleteEntity('identity:alice')

Each CRUD op becomes an immutable KernelOp (addFacts/deleteFacts/addLinks/deleteLinks) — the bridge to the causal stream.
