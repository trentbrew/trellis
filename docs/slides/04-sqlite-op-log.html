What Is the Causal Stream?

A Git commit is a snapshot of the entire repo at a moment in time. A Trellis op is a single semantic change — a fact asserted, a file modified, a branch created.

Git model

commits: [snapshot1] ← [snapshot2] ← [snapshot3]
                   ↑           full repo copy
                   every commit stores everything
                    (diff is derived, not stored)

Trellis model

ops: op1 → op2 → op3 → op4 → op5
        ↑
      each op is ONE change
      (add a fact, modify a file,
       create a branch, etc.)

  store = fold(allOps) → current state

Op Structure

Every operation is a self-contained envelope with a hashed payload:

export interface VcsOp {
  hash: string;          // trellis:op:{sha256}
  kind: VcsOpKind;       // e.g. 'vcs:fileAdd'
  timestamp: string;     // ISO 8601
  agentId: string;       // who asserted it
  previousHash?: string; // causal link → predecessor
  vcs?: VcsPayload;      // payload (HASHED)
  laneId?: string;       // envelope (NOT hashed)
  facts?: Fact[];        // envelope annotations (NOT hashed)
  links?: Link[];        // envelope annotations (NOT hashed)
}

// The hash covers:
// { kind, timestamp, agentId, previousHash, vcs }
// — NOT the envelope fields.

Envelope vs payload (TRL-102): envelope fields annotate an op without invalidating its hash. This lets peers annotate foreign ops (e.g. tagging them as "remote") while keeping provenance intact.

Op Kinds — Tiered Granularity

Ops are organized in three additive tiers of granularity:

TierGranularityOp Kinds
0File-as-blobfileAdd, fileModify, fileDelete, fileRename
1File-as-entitySame as Tier 0 + line-level metadata, language detection
2AST-as-graphsymbolRename, symbolMove, symbolExtract, signatureChange

Tiers are additive — a file change may produce both a vcs:fileModify (Tier 0) and a vcs:symbolRename (Tier 2), making the same change queryable at both levels.

VCS Control & Workflow Ops

Beyond file-level changes, the op log records structural and workflow operations:

Content-Addressed Hashing

Every op's hash is a SHA-256 digest of its content + causal predecessor. This makes the op log tamper-evident — rewriting any op invalidates every successor.

// hashVcsOp({ kind, timestamp, agentId,
//           previousHash, vcs })
const content = JSON.stringify({
  kind: 'vcs:fileAdd',
  timestamp: '2026-06-15T12:00:00Z',
  agentId: 'identity:alice',
  previousHash: 'trellis:op:abc123…',
  vcs: {
    filePath: 'src/auth.ts',
    contentHash: 'sha256:def456…',
  }
})

const hashBuffer = await crypto.subtle.digest('sha256', content)
// → hashHex: "trellis:op:9f3a7e…"

The hash is reproducible — given the same inputs, two peers minting the same semantic change produce identical hashes. This enables deduplication during sync.

On-Disk Format: JSONL

One op per line — newline-delimited JSON. Appends are atomic, preventing the "lost append" bug that plagued the old array format.

ops.json (JSONL)
{"hash":"trellis:op:001…","kind":"vcs:fileAdd","timestamp":"2026-06-15T12:00:00Z","agentId":"identity:alice","previousHash":null,"vcs":{"filePath":"src/index.ts","contentHash":"sha256:abc"}}
{"hash":"trellis:op:002…","kind":"vcs:fileAdd","timestamp":"2026-06-15T12:00:30Z","agentId":"identity:alice","previousHash":"trellis:op:001…","vcs":{"filePath":"src/utils.ts","contentHash":"sha256:def"}}
{"hash":"trellis:op:003…","kind":"vcs:branchCreate","timestamp":"2026-06-15T12:01:00Z","agentId":"identity:alice","previousHash":"trellis:op:002…","vcs":{"branchName":"feature-x"}}

Two processes can never clobber each other's writes — each simply adds its own line. Legacy JSON-array files are auto-migrated on first append.

Backend Abstraction

The OpLog interface is backend-agnostic. Implementations persist to filesystem (JsonOpLog), browser IndexedDB (IdbOpLog), or any store:

export interface OpLog {
  load(): void | Promise
  append(op: VcsOp): void
  readAll():       VcsOp[]
  getLastOp():    VcsOp | undefined
  count():        number
  flush?():       Promise
}

// Concrete implementations:
JsonOpLog     // JSONL on filesystem
IdbOpLog      // IndexedDB (browser)
LaneOpLog     // per-lane journal journal

The KernelBackend interface (SQLite) provides the same operations for the kernel: append, readAll, readUntil, readAfter, readUntilTimestamp, snapshot support.

Boot & Snapshots

The kernel boots by loading the latest snapshot, then replaying only ops after that snapshot — making startup fast even for large histories.

class TrellisKernel {
  boot(): { opsReplayed, fromSnapshot } {
    backend.init()

    const snapshot = backend.loadLatestSnapshot()
    if (snapshot) {
      store.restore(snapshot.data)      // hydrate from snapshot
      backend.readAfter(snapshot.lastOpHash)  // replay tail only
    } else {
      backend.readAll()                 // full replay
    }
  }

  checkpoint() {
    backend.saveSnapshot(lastOpHash, store.snapshot())
  }
}

// Snapshot = { facts, links, catalog }
// Triggered every N ops or on signal (green build, interval)

Per-Lane Op Journals

Agent lanes each have their own isolated op journal — a separate JSONL file. This enables multi-agent isolation without cross-contamination.

.trellis/
  ops.json        // integration journal (main branch)
  lanes/
    lane-a1b2…/
      ops.json    // lane journal
    lane-c3d4…/
      ops.json    // lane journal
  snapshots/
    snap-a1b2…/   // lane snapshots

When a lane is promoted (via trellis issue close --confirm), its ops are replayed onto the integration journal, and a milestone is auto-created.
