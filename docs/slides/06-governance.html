Identity as Graph Entities

Every actor — human, CI runner, bot — is an Identity entity in the graph, not a third-party auth server.

Entity: identity:alice
  ├─ type:        "Identity"
  ├─ displayName: "Alice Chen"
  ├─ publicKey:   Ed25519:x5mJ2…bQ1kP
  ├─ did:          "did:key:z6Mk…"
  ├─ createdAt:    "2026-05-15T…"
  └── memberOf:   org:acme     (link)

Entity: identity:ci-bot
  ├─ type:        "Identity"
  ├─ displayName: "CI Bot"
  ├─ publicKey:   Ed25519:aP9qR…vW3kL
  └─ did:          "did:key:z6Mi…"

The private key is stored never synced — only local. The public key and DID are graph entities replicated to peers for verification.

Op Signing

Every operation carries an Ed25519 signature over its hash. This provides non-repudiation and auditability.

// In VcsOp.vcs payload (inside the hashed preimage):
{
  signature: "ed25519:MEUCIQD9…",  // signature over op.hash
  signedBy:  "identity:alice",      // who signed
  signedWith: "device:laptop",      // which device held the key
}

// Creating a signed op:
const op = await createVcsOp('vcs:fileAdd', {
  agentId: 'identity:alice',
  vcs: {
    filePath: 'src/auth.ts',
    contentHash: 'sha256:abc…',
    signedBy: 'identity:alice',
    signature: await sign(op.hash, alicePrivateKey),
    signedWith: 'device:laptop',
  },
})

Unsigned ops use the self-asserted agentId — honest for local repos and tests, inadequate for multi-peer sync.

Signature Verification Middleware

A SecurityMiddleware intercepts incoming remote ops and verifies signatures before they reach the store:

class SignatureVerificationMiddleware
  implements KernelMiddleware {

  name = 'signature-verification'

  async handleOp(op, ctx, next) {
    // Skip verification for local ops (signed on creation)
    if (!ctx.remote) return next(op, ctx)

    const vcsOp = op as VcsOp
    if (vcsOp.vcs?.signature && vcsOp.vcs?.signedBy) {
      // Look up identity → public key
      const identity = resolveIdentity(vcsOp.vcs.signedBy)
      // Verify Ed25519 signature over the op hash
      const valid = verify(
        vcsOp.hash,
        vcsOp.vcs.signature,
        identity.publicKey,
      )
      if (!valid) {
        // Op is rejected — its hash is invalid
        throw new Error(
          `Invalid signature on op ${op.hash}`
        )
      }
    }

    return next(op, ctx)
  }
}

Policy Entities in the Graph

Branch protection and governance rules are expressed as Policy entities — stored as EAV facts, queryable via EQL-S.

Entity: policy:protect-main
  ├─ type:           "Policy"
  ├─ target:         "branch"
  ├─ targetPattern:  "main"
  ├─ action:         "push"
  ├─ minSignatures:  2
  ├─ requiredSigner: "identity:alice"   (multi-valued)
  ├─ requiredSigner: "identity:bob"
  └─ requireAttestation: { type: "test-pass", from: "identity:ci-runner" }

This is how Trellis makes governance declarative: policies are data, not code. You can query, version, and branch them like anything else.

Governance Middleware Flow

┌─────────────────────────────────────────────────────┐
│  Middleware Chain (kernel level)                     │
│                                                      │
│  ┌─ SignatureVerificationMiddleware                 │
│  │  • Verify Ed25519 signatures                       │
│  │  • Reject forged ops                               │
│  └─►                                                 │
│     ├─ GovernanceMiddleware                           │
│     │  • Find applicable policies                     │
│     │  • Check signature requirements                 │
│     │  • Check attestation requirements               │
│     │  • Reject unauthorized ops                      │
│     └─►                                               │
│        ├─ SchemaValidationMiddleware                 │
│        │  • Enforce ontology schemas                   │
│        └─►                                             │
│           ┌─ DecompositionMiddleware                 │
│           │  • VcsOp → EAV primitives                   │
│           └─►                                           │
│              └─ EAVStore + Backend (apply)             │
└─────────────────────────────────────────────────────┘

The KernelMiddleware interface uses (op, ctx, next) chaining — each middleware can accept, reject, or transform an op before it reaches the store.

Zone Capability Model (ADR 0022)

Zones are authority-bearing containers with capability levels. Grants are stored as facts with bounded domains (Reader|Member|Owner) so they can be exhaustively enumerated.

// Zone entity (authority is in the ID, derived not asserted):
Entity: zone:turtle://did:key:z6Mk…/zone/abc123
  ├─ type:              "Zone"
  ├─ zoneId:            "turtle://…/zone/abc123"
  ├─ alias:             "my-zone"
  ├─ parentZone:        "turtle://…/zone/parent"  (inherits grants)
  ├─ defaultVisibility: 0  (Reader = public)
  ├─ grant:identity:alice: 3   (Owner)
  ├─ grant:identity:bob:   2   (Member)
  └─ grant:identity:carol: 1   (Reader)
  // Levels: None(0)=absent, Reader(1), Member(2), Owner(3)

Grant changes are always delete-then-add over the bounded domain — no stale values linger. Revocation removes the fact rather than writing None.
