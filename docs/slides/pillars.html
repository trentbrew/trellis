The Five Pillars of Trellis

Local-first semantic graph OS — built on an inspectable causal substrate

What Is Trellis?

A local-first agentic OS runtime: a personal and collaborative semantic graph where files, entities, facts, links, decisions, agents, branches, and milestones live in one inspectable causal substrate.

Local ownership is primary

Trellis is fully useful without a cloud server. Local state, local identity, local persistence, and local query execution are the default. Cloud services, relays, and gateways are additive.

Sync is replication, not ownership transfer

Peer sync replicates signed, causally ordered operations between Trellis nodes. A relay may help peers connect but does not own state.

5 Pillars Agentic OS

Pillar 1: The Causal Stream

A fine-grained, immutable ledger of every semantic change

Every change — from a file save to a branch creation — is recorded as a VcsOp in the append-only stream. The stream is:

  • Immutable — ops are never modified or deleted
  • Causally ordered — each op references its predecessor via previousHash
  • Content-addressed — each op's hash covers its content + causal link (SHA-256)
  • Agent-attributed — every op carries an agentId (human or CI)
// Each op is a node in the causal DAG
{ kind: 'vcs:fileAdd',
  timestamp: '2026-06-15T12:00:00Z',
  agentId: 'identity:alice',
  previousHash: 'trellis:op:abc123…',
  hash: 'trellis:op:def456…',
  vcs: { filePath: 'src/auth.ts', contentHash: 'sha256:…' }
}

Pillar 2: Semantic Patching

Understanding code as a tree (AST), not lines of text

Instead of treating changes as line diffs, Trellis records changes as structured semantic patches that describe what happened in terms of code structure.

  • A variable rename across 47 lines is one symbolRename op, not 47 line-level edits
  • Two patches commute when they operate on disjoint entities
  • When they conflict, the result is a structured conflict naming the entities involved — not <<<<< text markers
type SemanticPatch =
  | { kind: 'symbolAdd'      entity: ASTEntity }
  | { kind: 'symbolRemove'   entityId: string }
  | { kind: 'symbolModify'   entityId, oldSig, newSig }
  | { kind: 'symbolRename'   entityId, oldName, newName }
  | { kind: 'symbolMove'     entityId, oldFile, newFile }

Pillar 4: The Governance Subgraph

Identity and permissions built into the data structure

Identity Model

Every actor (human, CI runner, bot) is an Identity entity with an Ed25519 key pair. The private key stays local; the public key + DID are graph entities replicated to peers.

{ e: 'identity:alice',
  a: 'type',        v: 'Identity'
  a: 'publicKey',   v: 'ed25519:…'
  a: 'did',         v: 'did:key:z6Mk…'
}

Op Signing

Every op carries an Ed25519 signature over its hash. A signing middleware verifies incoming remote ops. Policy rules live as graph entities too — branch protection, merge gates, attestation requirements.

Pillar 5: The Idea Garden

A permanent, searchable archive of all exploration

In Git, abandoned work (stale branches, lost commits) is invisible. In Trellis, the causal stream is immutable, so abandoned work remains in the stream. The Idea Garden is a query layer that surfaces, clusters, and makes abandoned exploration searchable.

  • Context-switch detection: When files being modified shifts abruptly, preceding un-milestoned ops form a candidate cluster
  • Branch abandonment: Stale branches' un-milestoned ops are flagged
  • Revert detection: Ops followed by undo-ops form a cluster
# Discover abandoned work
trellis garden list
trellis garden search -k "auth caching"
trellis garden revive <cluster-id> --branch "retry-caching"

Runtime Architecture

The target shape: NixOS host → Turtle runtime service/sidecar → Trellis kernel → sync transports → client surfaces.

NixOS / host system
  → Turtle runtime service or sidecar
    → Trellis kernel
      → EAV graph store
      → causal op log
      → query engine
      → blob store
      → identity and governance
      → local live subscriptions
    → sync transports
      → Iroh peer-to-peer
      → local memory transport
      → optional WebSocket / PartyKit relay
    → client surfaces
      → Tauri desktop shell
      → CLI
      → MCP
      → TypeScript SDK
      → browser gateway

Invariants: works without cloud server · local state is primary · every mutation is a durable op · peers validate through identity & causal history · relays are optional adapters.
